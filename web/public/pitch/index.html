The question every Walrus deck must answer

Anyone can put one image on Walrus
and call it “decentralized.”

That's the bar most submissions clear — and stop at. One blob, one screenshot, one press release. We think that misreads what Walrus is for. Walrus is a content backend, not a demo prop. So we asked a harder question:

What would a real consumer app look like if Walrus held everything users actually read?

The thesis

Walrus is the entire content backend.
There is no content database. Anywhere.

Public metadata, media, and Seal-encrypted private data — all on Walrus, across eight distinct use cases, on a single 49-line SDK-free HTTP client. No Postgres, no S3, no websocket holding content behind it.

Suithe index & the truth — identity, ownership, logic, access policy. The on-chain event log is the only record of where content lives.
Walrusthe store — every byte anyone actually reads: public metadata, media, art, reviews + encrypted forum, vault, drafts, AI memory.
Sealthe lock — threshold encryption on the private subset, released only when a Move policy passes.
The showstopper · provable in one assert

A HostIt event that doesn't live on Walrus
literally cannot exist.

sources/event.move — fn create_event
// an Event is deliberately thin…
public struct Event has key {
  name, start_ms, end_ms, max_tickets, flags,
  uri: String,   // ← nothing but a Walrus blob id
}

// …and the constructor refuses an empty uri:
assert!(string::length(&uri) > 0, E_EMPTY_URI);
// every Event MUST point at a Walrus blob

The mint aborts with E_EMPTY_URI if you try to create an event without a Walrus blob id. Sui state is structurally incomplete without Walrus — a property you prove by reading one line and trying to violate it, not a claim you take on faith.

  • TTTL is first-class — 10 epochs default, 30 for drafts that must outlive a session.
  • ⇄Dedup handled — newlyCreated vs alreadyCertified resolved transparently.

Walrus + Seal · the headline pairing

One encrypted blob. Two on-chain policies.
Access composes; content stays single-copy.

Seal.encrypt(message, event_id) → Walrus.store({id, ct}) → forum::post(blob_id) anchors it on-chain
 
decrypt the same ciphertext via either Move policy:
  ✓ seal_approve_ticket  — a ticket holder   OR  ✓ seal_approve_organizer  — the OrganizerCap
  • ⛓Authorization composes on-chain — two independent Move policies, one blob. Neither party re-encrypts.
  • ⦿The aggregator only ever sees ciphertext. Walrus holds exactly one copy; Seal holds the key; Sui decides who gets it.
  • ⊘Namespacing is real — organizer-only data is domain-separated, so a ticket-holder policy can never decrypt it.
Immutability, done right

We embrace Walrus's permanence
instead of fighting it.

A post is an immutable event plus an immutable blob — so moderation is by tombstone (PostModerated, keyed on the blob id), never deletion. No content database means no takedowns, no silent edits, no platform that can rewrite your event's history. Permanence isn't a constraint we worked around. It's the property that makes the whole thing trustworthy.

The engineering centerpiece

Bet on whether it sells out — settled trustlessly, no oracle.

Every event opens native parimutuel markets: a Sellout Clock and a final-tickets-sold range. They settle by reading the contract's own event::minted() at expiry — anyone can settle; goalposts are snapshotted at creation so they can't move.
